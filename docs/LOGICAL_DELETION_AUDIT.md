# 論理削除・履歴保持の全体監査

最終更新: 2026-10-21

## 結論

`packages/db/src/schema` の SQLite テーブル55個をすべて確認し、削除を扱う API、状態遷移、外部キー、イベント終了後の保持処理を照合した。履歴・参照を保護すべき通常操作の物理削除漏れは、今回の修正対象4領域である。

- 来訪実績: レビュー資格と店舗統計を保つ論理削除・復元
- スタッフ: 過去記録からの参照を保つ利用停止・復元
- イベント送信履歴／システムお知らせ: 配信記録を保つアーカイブ・復元
- 契約入金: 台帳行を訂正済みとして保ち、合計から除外
- 抽選景品: 当選者の参照を保つ既存アーカイブに復元 UI/API を追加

全データを論理削除にするのではなく、認証秘密、可変の下書き、単なる権限の紐付け、期限付きセッションなどは目的に応じて物理削除する。イベント終了後の一括消去は論理削除とは別の保持期限処理として判定した。

## 監査範囲と方法

- `auth.ts`、`core.ts`、`menu.ts`、`order.ts`、`visitor.ts`、`lottery.ts`、`system.ts` で定義される全55テーブルを列挙
- API ルートおよびサービスの `DELETE` / `db.delete` / SQL `DELETE`、関連画面の削除操作を検索して確認
- 外部キーの `ON DELETE`、スナップショット、状態列、イベント保持処理と照合
- コードの静的監査。Cloudflare 本番データや本番 API に対する削除・復元の実行確認はしていない

## テーブル別判定（55テーブル）

判定の意味: **論理/状態** = 業務履歴を残したまま非表示・利用停止にする、**保持後 purge** = 通常操作では消さず、イベント等の保持期限後だけまとめて消す、**物理削除可** = 秘密・一時状態・可変設定などを除去してよい。

### 認証（5）

| テーブル | 判定 | 理由・運用 |
|---|---|---|
| `user` | 物理削除可 | 本人のアカウント消去で認証主体を削除する。`session` / `account` / `passkey` は FK cascade。監査ログ等に残るメールアドレスの保存期間は別の個人情報保持方針で管理する。 |
| `session` | 物理削除可 | 期限切れ・ログアウト時に認証資格を無効化する一時データ。期限切れ掃除 API がある。 |
| `account` | 物理削除可 | OAuth / パスワード等の認証資格情報。ユーザー削除に連動して消す。 |
| `verification` | 物理削除可 | 期限付き検証コード。期限切れ後に復元する業務履歴ではない。 |
| `passkey` | 物理削除可 | 認証用資格情報。ユーザー削除時に cascade する。 |

## 今回の修正内容

- `circle_visit.deleted_at` を追加し、来場者編集画面から利用実績を無効化/復元。レビューの利用資格とサークル利用統計は無効行を除外する。
- `staff.deleted_at` を追加し、名簿の通常一覧から除外。削除済み一覧は権限を確認して表示し、復元可能にする。
- `event_announcement.deleted_at` を追加。履歴を隠して復元しても、来場者へ配信済みの通知はそのまま残す。
- `announcement.deleted_at` を追加。削除時に未公開化し、復元後も自動再公開しない。
- `contract_payment.voided_at` / `voided_by` を追加。訂正行は台帳に残し、契約入金の合計から除く。
- 既存の抽選景品アーカイブに復元 UI/API を追加し、抽選後は変更できないよう API でも確認する。
- D1 migration: `0044_misty_giant_girl.sql`。本番・リモートDBには適用していない。

## 保持期限処理の範囲と未決定の運用事項

現在の `apps/api/src/services/cleanup.ts` は、終了日から設定された日数（既定365日、30〜3650日）を超えた `ended / archived` イベントについて、`orders`、`pre_order`、`circle_visit`、`numbered_ticket`、`review`、`user_stamp`、`event_user`、`lottery` を purge し、FK cascade による子行削除を許す。削除ゲートは `CLEANUP_ENABLED === "true"` が必要で、`CLEANUP_DRY_RUN === "true"` なら実行しない。

これは復元用の論理削除とは別の不可逆な保持期限削除である。今回の監査では、次を既存 cleanup に勝手に追加していない。保持期間や法務・運用要件を決めてから別途変更する。

- `wristband_batch` / `wristband_batch_chunk`: QR URL を含み得る発行ログの保管期限・失効後の消去
- `notification` / `visitor_notification`: 既読通知を含めた通常保持期間
- `audit_log`: 監査要件とメールアドレスの個人情報保持期間
- `contract_payment`: 財務・契約書類として必要な保持期間
- `order_sequence` / `event_user_sequence`: 対応する注文・来場者履歴を purge した後の採番行整理
- ユーザーのアカウント消去後も、`audit_log`、`recorded_by` 等のメールアドレスが残る範囲と匿名化条件

以上は「論理削除がない不具合」とは切り分けた保持方針の課題である。特に QR URL と個人情報を含むログは、イベント終了後のデータ削除だけでは全テーブルから消えたと見なせない。
